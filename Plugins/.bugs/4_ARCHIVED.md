- [x] **[PLG-001]** `[UI & Threading]` `.ConfigureAwait(false)` in UI code-behind - `Plugins/ViveTool/ViveToolPage.xaml.cs` (15 sites reported at L628..L1192). **Closed 2026-07-06.**
  - **Root cause**: UI code-behind awaited service calls with `.ConfigureAwait(false)`, stripping the captured `DispatcherSynchronizationContext`. The page already marshals UI touches through `await Dispatcher.InvokeAsync(...)`, so there was no live cross-thread race, but the pattern drifted from the repo thread-safety contract (workflow #6.A.1) and would regress if a future edit added direct control access between awaits.
  - **Fix**: A concurrent editor removed all 15 `.ConfigureAwait(false)` sites from the working tree. The sole remaining await hint is `.ConfigureAwait(true)` at L829 (`await RefreshPageAsync(...)`), which is UI-safe (explicitly re-captures the dispatcher context) and satisfies the "zero `.ConfigureAwait(false)` in `**/*.xaml.cs`" rule. No code change was required in this handover session.
  - **Verification**: `rg -g '*.xaml.cs' 'ConfigureAwait\(false\)'` => 0 matches across all plugins; `dotnet build UniversalDeviceToolkit-Plugins.sln -c Release` => 0 warnings / 0 errors; `dotnet test <solution> -c Release --no-build` => 409 passed / 0 failed / 0 skipped (CustomMouse 54, ShellIntegration 114, BatteryHealth 16, NetworkAcceleration 39, ViveTool 186).
  - **Preventative rule (transcribed to `KNOWLEDGE_BASE.md`)**: Forbid `.ConfigureAwait(false)` in `**/*.xaml.cs` via a CI grep gate; UI code-behind must rely on the captured `DispatcherSynchronizationContext` (omit the hint, or use `.ConfigureAwait(true)`). Only Lib/SDK/non-UI code may use `.ConfigureAwait(false)`.
 - **Non-ticket audit (carried over)**: The bug reporter audited other plugin areas as clean - `NetworkAccelerationPlugin.RunCommandAsync` and `ShellIntegrationPlugin.RunShellCommandAsync` both bound execution via explicit process/CTS timeouts; their `CancellationToken.None` public overloads forward to the token-aware methods (not defects).

- [x] **[PLG-002]** `[Test Isolation]` xUnit parallelism race on `Resources.Resource.Culture` static - metadata test reads culture-dependent text while a sibling test flips the ambient culture. **Found & Fixed 2026-07-06.**
  - **Root cause**: `LocalizedTextTestsBase.TextClass_HasNoHardcodedChinese` mutates the process-wide static `Resources.Resource.Culture` to `en` via reflection (restored in `finally`). xUnit runs each plugin's `*TextTests` concurrently with its sibling `*PluginTests`. The metadata assertion `Assert.Equal(XText.PluginName, plugin.Name)` resolves the culture-dependent property twice; a parallel text test flips the static null to en between the two reads, so one read returns the zh-Hans ambient value and the other the en value. Symptom: `BatteryHealthPluginTests.Plugin_HasExpectedMetadata` failed with Expected: 电池健康 vs Actual: Battery Health only under the full-solution parallel run (passed in isolation). Latent in CustomMouse, NetworkAcceleration, and ShellIntegration (same tautological two-read pattern); ViveTool immune (uses IsNullOrWhiteSpace + already serialises its test collection).
  - **Fix**: Per plugin, place `*TextTests` and `*PluginTests` in the same non-parallel collection via `[CollectionDefinition("<Plugin>ResourceCulture", DisableParallelization = true)]` plus `[Collection("<Plugin>ResourceCulture")]` on both classes (repo STA idiom). Added 4 new collection-definition files (BatteryHealth / CustomMouse / NetworkAcceleration / ShellIntegration) and tagged the 8 test classes.
  - **Verification**: `dotnet build UniversalDeviceToolkit-Plugins.sln -c Release` => 0 warnings / 0 errors; `dotnet test <solution> -c Release --no-build` => 409 passed / 0 failed / 0 skipped (CustomMouse 54, ShellIntegration 114, BatteryHealth 16, NetworkAcceleration 39, ViveTool 186).
  - **Preventative rule (transcribed to `KNOWLEDGE_BASE.md`)**: Never assert culture-dependent properties with a tautological two-read pattern (`Assert.Equal(XText.P, plugin.P)`) while a sibling test mutates the shared static culture. Pin test-class siblings that share a mutable static into one `[CollectionDefinition(DisableParallelization = true)]` and tag both the writer (TextTests) and reader (PluginTests) classes.
- [x] **[PLG-003]** `[UI Governance]` Modal `MessageBox.Show` in plugin UI code-behind - `Plugins/ViveTool/ViveToolSettingsPage.xaml.cs` (6 dialog sites) + `Plugins/ShellIntegration/ShellIntegrationStyleSettingsWindow.cs:135`. **Closed 2026-07-06.**

- [x] **[PLG-004]** `[Threading & WMI]` `BatteryHealthService.QueryFirst` enumerated `ManagementObjectSearcher.Get()` synchronously; the outer `cts.CancelAfter(3000)` could not interrupt a hung native COM/WMI provider, so a stuck ACPI/WMI provider pinned the thread-pool task past the 3s timeout contract. **Closed 2026-07-06.**
  - **Root cause**: `BatteryHealthService.QueryFirst` enumerated `ManagementObjectSearcher.Get()` synchronously on the calling thread. The outer `cts.CancelAfter(WmiTimeoutMs=3000)` is decorative for a hung WMI provider because native COM enumeration does not observe the `CancellationToken`. The defect was present both at HEAD `6165cd5` (synchronous `Get()` with no timeout at all) and in the worktree refactor that added the `CancelAfter` plumbing.
  - **Fix**: Bound the enumeration off-thread in `Task.Run` and race it against a hard 2,500ms deadline (the abandon pattern used by the host-side `ManagementObjectSearcherExtensions.GetAsync`); on deadline -> `cts.Cancel()` + throw `TimeoutException`; on enumeration fault unwrap `AggregateException` to preserve `ManagementException` / `COMException` / `OperationCanceledException` so the typed catch blocks of the caller still match. Added per-query `WmiQueryTimeoutMs = 2500`; outer `WmiTimeoutMs = 3000` retained as the total budget ceiling.
  - **Verification**: `dotnet build UniversalDeviceToolkit-Plugins.sln -c Release` => 0 warnings / 0 errors; `dotnet test Plugins\BatteryHealth.Tests --no-build` => 16/16 pass.
  - **Preventative rule (transcribed to `KNOWLEDGE_BASE.md`)**: Never rely on `cts.CancelAfter` alone to bound a synchronous native COM/WMI enumeration (`ManagementObjectSearcher.Get()`); the `CancellationToken` is not observed by the native enumerator. Run the enumeration off-thread (`Task.Run`) and race it against a hard wall-clock deadline (`Task.Wait(TimeSpan)` abandon pattern), throwing `TimeoutException` on expiry. Unwrap `AggregateException` to preserve original typed exceptions for caller catch blocks. Reference: host-side `ManagementObjectSearcherExtensions.GetAsync` (`Task.WhenAny(task, Task.Delay(timeoutMs))` + abandon).

### PLG-005 [Cross-Assembly Test Flakiness] NetworkAcceleration SaveAsync file contention
- **Filed**: 2026-07-07
- **Fixed**: 2026-07-07
- **Root Cause**: Host `PluginConfiguration.SaveAsync()` writes to a shared temp config path. Cross-assembly parallel xUnit test execution causes `IOException` (file locked). Passes 100% when run solo.
- **Fix**: Added retry-with-backoff (3 attempts, 50ms/100ms delays) wrapping `Configuration.SaveAsync()` in `NetworkAccelerationPlugin.SaveSettingsAsync()`.
- **Verification**: Full solution: 409/409 pass. Solo: 39/39 pass. Build: 0W/0E.
- **Rule**: All plugin `SaveSettingsAsync()` methods calling `Configuration.SaveAsync()` MUST wrap in retry-with-backoff. Root fix belongs in host library.
