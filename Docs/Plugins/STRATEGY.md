# Plugin Strategy — 设备能力，不是工具抽屉

插件系统的前途不是商店变大，而是让 UDT 在「官方还没写进 Host 的那块硬件」上仍然可信。商店可以薄，目录可以少，但每一项都应该是**设备能力**，不是工具抽屉。

## 定位与边界

UDT 的对外叙事是「可信本机硬件控制」。据此划分：

| 层 | 职责 | 判据 |
| --- | --- | --- |
| **主程序（Host）** | 通用、可预期、可被 `udt` CLI/RPC 稳定调用的能力：电源模式、RGB、电池、托盘、Fn+Q、传感器 | 默认路径；不经插件 |
| **品牌 provider** | 主流机型 EC/WMI/厂商协议，进主仓 `UniversalDeviceToolkit.Lib/DeviceSupport` | 有真机协议才声称（见 [DEVICE_PROVIDERS.md](../DEVICE_PROVIDERS.md)） |
| **插件** | 机型/外设/厂商**特例**，独立发版 | 只有必须进进程、必须碰设备、或必须长期驻留的能力 |

可以装插件 ≠ 应该用插件商店讲产品。基础模式里插件还能用，那是诚实降级，不是增长支柱。

不要和主程序抢「清理缓存、改系统设置、网络加速」这类 AI 和系统 API 越来越便宜的事——网络加速从插件移入 Host（v5.0.0）就是正确方向的先例。

## 三条发展轨

### 1. 硬件/外设插件（主轨）

灯带、鼠标、壳灯、小厂商 EC 特例、某代键盘私有协议。

**判断标准：没有这份代码，用户就控不了这块硬件。**

这类插件和品牌 provider 是同一类资产，只是交付形态不同：

- provider 进主仓，随主版本发布
- 插件走 `plugin-catalog` 独立发版，验证周期更短

现状对齐：`custom-mouse`（外设控制）站得住。

### 2. 驻留集成（严选）

托盘旁的壳菜单、必须挂钩输入的键鼠映射。可以留，但必须同时满足：

- 必须进进程或长期挂钩（不是改一次注册表/开关）
- 用户每天会用，且不想每次问 AI

现状对齐：`shell-integration` 已从商店下架（`Removed`），存量用户可用；是否回流取决于真实驻留刚需证据，不扩投入。ViVeTool 这类「改一次 Windows 开关」更像脚本，不再当生态门面。

### 3. 给 Agent 的能力扩展（辅轨）

插件若要长期有价值，最终应能挂到与 `udt-cli` 同一套 CLI/RPC 允许列表上，而不是只给 Electron 多一个设置页。

- Agent 调用的是「这块灯 / 这只鼠标」，不是「再打开一个网页」
- 新插件的 C# 能力在设计时就规划窄接口：默认关、按显式动作触发、失败可回滚、能被 `doctor` 探测
- 参照 `Docs/CLI.md` 的命令面纪律：机器可读输出（`--json`）、无 IPC 自检、退出码稳定

**明确不做第二套 UI**：`contributes.webPage` 只承载该插件的可视化配置，不复制 Host 已有能力。

## 明确不做

1. 用插件补「任何 PC 都能用的系统优化」
2. 为了目录好看而堆官方插件数量
3. 插件 UI 与 Host 功能重复（两个地方都能改同一件事）
4. 把签名、目录、商店运营做成比硬件正确性更重的投入
5. 让插件成为增长叙事的门面（README/推广不以插件数量为亮点）

## 准入筛子（官方目录门槛)

每个新插件提案进官方目录前过三问，**全部通过才收**：

| # | 问题 | 不过的理由 |
| --- | --- | --- |
| 1 | 离开真机/驱动/私有协议，AI 写个脚本是不是就够？ | 够 → 做脚本，不做插件 |
| 2 | 用户会不会反复用，而不是装一次？ | 一次性 → 不值得驻留进程 |
| 3 | 能不能安全地暴露成和 `udt` 一样的窄接口（默认关、可审计）？ | 不能 → 无法进入 Agent 允许列表，也没有人用热路径 |

过不了的让社区自建，主仓不背书、不进 `plugin-catalog`。

现有官方方向的判定基线：

| 插件 | 筛子结果 | 处置 |
| --- | --- | --- |
| `custom-mouse` | 硬件主轨，需补 Agent 窄接口设计 | **保留并按主轨演进** |
| `vive-tool` | 第 1 问不过（脚本即可） | **保留但不宣传**；未来可标 `Removed` |
| `shell-integration` | 驻留价值待真机数据证实 | **已下架**；无证据不回流 |

## 目录与运营收敛

- `plugin-catalog` 只收主轨 + 严选通过的插件；preview 渠道同一标准
- 商店指标从「多少个插件」改为「多少台真机被可信覆盖」
- 官方目录数量预期是个位数——这是特性不是缺陷
- 退市路径：manifest `lifecycle: Removed`（已有 `StoreJsonGenerator` 支持），存量安装继续可用

## 评估口径（两个季度滚动)

| 维度 | 指标 | 说明 |
| --- | --- | --- |
| 硬件覆盖质量 | 「声称可控」vs Issue 真机稳住的比例（按机型） | provider 与插件共用此口径 |
| 能力调用 | `udt` / 自动化 / 宏 对设备能力的调用次数 | 「AI 会不会来用」的先行指标；插件计数含其 RPC 前缀调用 |
| 叙事一致性 | README/PROMOTION 是否仍以插件数量为卖点 | 出现即回退 |
| 不做清单 | 每季度移出路线图的「AI 脚本就够」提案数 | >0 才说明筛子在起作用 |
